## 43. A global initialised with an import's address (implemented at 178)

`p: :imp-fn` — a Red/System static initializer holding the address of an
imported function — used to die in codegen on both backends. It now works on
Windows-X86-64, Darwin-ARM64, Linux-X86-64 and Linux-ARM64.

Design: functions, globals and imports already share one reference-id space in
that order, so the initializer's reference rides in the slice the import's own
calls already use, distinguished by sign — positive = code offset to patch,
negative = 1-based position of a data slot for the loader to fill (the same
encoding `load-codegen` already uses for a data reference).

- ARM64: new arm in `valid-static-address-initializer?` + `target-id` via the
  new `static-address-target-id` helper (shared by its three call sites).
- x64: same, plus the reference must be *counted* in `measure-module-functions`
  under `argument-marking?`, or an import whose address is only taken gets no
  slice. `place-module-globals` just returns 0 for it.
- PE: an extra `IMAGE_IMPORT_DESCRIPTOR` per slot (library name reused,
  one-entry ILT + null, `FirstThunk` aimed at the slot) — there is no PE
  relocation that resolves a name after loading.
- ELF: one `R_*_GLOB_DAT` per slot in `.rela.dyn`, symbol index = 1-based
  position in the flat import list (= its `.dynsym` index).
- Mach-O: one extra bind opcode per slot at the data offset.

Baseline: `hybrid-compiler179.exe` (178->179, 6408192 bytes). Fixed point 179
vs 180 = the usual 17 bytes of clock noise. Red/System suite 10593 tests /
12680 assertions / 12680 passed / 0 failed / 0 compile-failures.

### The PE rule that cost the most time

**The loader skips a thunk whose IAT slot does not still hold the lookup
table's own hint/name RVA** — it reads that as an entry an earlier bind
already filled. A `.data` slot left at zero is therefore *silently* left at
zero, with no error. Seeding the slot with the ILT entry's value (what a real
IAT slot holds before snapping) makes the loader fill it. Proved by
binary-patching `FirstThunk` in a built `.exe`: seeded -> filled at every
`.data` address tried; zeroed -> filled at none.

## 47. Linux-X86-64: struct-by-value is passed by reference and reordered

The probe that verified the new libs turned up a real backend bug.
`checkTriple8 [t [triple8! value] bias [integer!]]` on Linux-X86-64 emits

    mov $0x4,%edi          ; bias -> RDI
    lea 0x10(%rsp),%rsi    ; &t    -> RSI
    call checkTriple8

System V wants the 3 bytes in RDI and the bias in RSI. Results: 290 instead
of 10, and `checkBig` 0 instead of 1. Darwin-ARM64 10/1, Linux-ARM64 10/1,
Windows-X86-64 10/1 — so it is the System V classification in x64-codegen
only. Not yet fixed.

### Traps

- `run.sh` must invoke `./$f`. A bare `"$f"` makes the shell search PATH and
  every unit exits 127 -- which looks exactly like "the binaries are broken".
- `scp -r` drops the execute bit; `chmod +x` on the Mac side.
- The 40-unit macOS R/S slice is the 43-entry list in `run-red-system-tests.red`
  minus `struct-test`, `size-test` (need `structlib.dll`) and
  `dylib-auto-test` (generated with host absolute paths).

- `resolve-import-refs` in ELF.red patches *code* at every entry of an import's
  reference list, so a negative (data-slot) entry lands at the head of `.text`
  and corrupts the entry point. Symptom: SIGSEGV two bytes into `***_start`,
  with `49 89 e4 55` overwritten. PE and Mach-O already skipped non-code
  entries for the same reason.
- Comparing against a control binary (same program without the feature) is
  what localised it; `readelf -r` showed the relocation was correct all along.

## System V aggregate ABI — done (commits 850a06b9c, be9d19f87)

`struct-x64-test` is now the acceptance test on every 64-bit target.

- **The bug**: x64-codegen applied the *Win64* aggregate rule on every target
  (1/2/4/8 bytes -> one integer register, anything else by reference, both
  classes from one shared slot counter). System V splits an aggregate of <=16
  bytes into eightbytes and gives each an integer or a vector register by what
  it holds, from *independent* counters (6 GPR, 8 XMM); larger, or exhausted,
  goes to memory. Returns differ too: RAX then RDX and XMM0 then XMM1, each
  class from its own pair, MEMORY return on a hidden pointer in **RDI**.
- **The shape of the fix**: classify per eightbyte in
  `sysv-aggregate-eightbytes`; one helper, `sysv-claim-argument`, owns the
  register counting for *all five* boundaries (copy pass, argument loop,
  `plan-storage`, prologue, return path) so they agree by construction.
- **Two traps, caught only by assertion totals**: (1) the copy pass and
  `plan-storage` reserve an argument's stack slot **before** the claim counts
  it out, so `stack-offset` in the argument loop must come from that same
  pre-claim slot — using the running one put every register-missing argument
  8 bytes high (this was the last 5 failures); (2) a hidden return pointer
  takes the first integer register on both ABIs, so the caller's GPR counter
  starts at `hidden-shift`, not 0 (this was 29 of them).
- **Results at 182/184**: Windows-X86-64 621/621, Linux-X86-64 621/621 (was 5
  failures + an access violation), Linux-ARM64 627/628 (pre-existing;
  `x64-codegen/generate` accepts only ABI_WIN64/ABI_SYSV so ARM64 never
  reaches the new code). Red/System suite unchanged at 10593/12680/12680/0.
  Linux-X86-64 slice 40/40 compile, 40/40 run, 0 differed. Fixed point: 182
  vs 183 differ in 16 bytes, all build clock (PE timestamp, checksum, two
  `movabs rax` immediates, output file name, two `dd-Mmm-yyyy/h:mm:ss`).
- **structlib wiring**: `struct-x64-test.reds` now names the 64-bit builds
  (`structlib.dylib` on macOS; `structlib-arm64.so` vs `structlib.so` by
  `target` elsewhere; Windows keeps `structlib.dll`). Nested `#switch` inside
  `#switch` works in the Red/System preprocessor. `struct-test.reds` is the
  32-bit unit and keeps the i386 names.
- **Mac was unreachable all session** (`ssh macmini` -> banner exchange time
  out on 127.0.0.1:5588). Darwin-ARM64 is compile-verified only.

## ARM64 stack slot width — fixed (commit 0ca8defd6)

`struct-x64-test` is now clean on every runnable 64-bit target.

- **The bug**: AAPCS64 gives every stack argument a whole eight-byte slot,
  but `abi-parameter-location` (arm64-codegen.reds) advanced the offset by
  the natural `width` — 4 for `integer!`/`float32!`. `checkBigOverflow 1 2 3
  4 5 6 7 s3 8 42` (seven ints fill x0-x6, so the 16-byte `big!` and both
  trailing ints spill) wrote `marker` at sp+20; gcc puts it at **sp+24**.
- **How it was found**: instrumented the failing group with `print ["@N"]`
  before each assertion — `--assert` is a *function*, so quick-test prints
  `FAILED` immediately, and the marker right before it names the assertion.
  (Assertions 51+ live inside helper *functions*, so their markers repeat;
  that is not a re-run.) Then objdump'd the call site against `gcc -O2 -c`
  for the same C call.
- **The fix**: advance by `align size 8`, align to `max(alignment, 8)`.
  `abi-trailing-argument` already did exactly this and its comment stated
  the rule — the fixed-parameter path just did not follow it.
- **Why only the native boundary noticed**: both sides of a
  Red/System-to-Red/System call ask the same function, so internal calls
  were self-consistently wrong.
- Linux-ARM64 627/628 -> **628/628**; its 40-unit suite still 0 failed
  assertions; Windows Red/System suite still 12680/12680/0. Fixed point:
  185 vs 186 differ in 18 bytes of build clock.

### Traps

- `ssh macmini` is a **local port-forward** (127.0.0.1:5588). When it fails
  with "banner exchange timed out", check `netstat` — if nothing listens on
  5588 the tunnel is down and there is no way to bring it up from here.
- To attribute a quick-test failure, put `print ["@N" lf]` before each
  `--assert`; the FAILED line prints immediately after the guilty marker.

## Windows View / gui-console: root cause found and fixed (189/190)

Two independent blockers, both fixed. `build/tmp-imp/gui-console.exe` (built
by `red-toolchain-190.exe -r`, 3319296 bytes) now opens a window and runs.

1. **UTF-16 literals were emitted at odd addresses.** `#u16` was interned as
   `[array byte N 1]`; an inline array takes its alignment from its element
   width (`layout-type`, kind = -7), so alignment was 1 and one odd-length
   predecessor left the next literal odd. The kernel probes every `WCHAR*`
   with its own alignment -> STATUS_DATATYPE_MISALIGNMENT -> user32 reports
   **ERROR_NOACCESS (998)**, which is why `RegisterClassExW`/`CreateWindowExW`
   failed. Proof: `build/tmp-imp/args27.reds` registers the *same* bytes from
   an even heap address (ok) and from that buffer `+1` (998).
   Fix: `add-static-bytes/wide` in compiler/rsir-frontend.red interns as
   `intern-array -4 ((length? data) / 2) 2`; the bytes-initializer check in
   system/codegen/x64-codegen.reds (site 303) and arm64-codegen.reds (site 27)
   now accepts element width 2, not just 1.
   Earlier "it's the stack" hypothesis is dead: the PE commits all 8 MB, every
   call site is 16-byte aligned, and cdb catches no AV/SOV/SBO.

2. **The Windows View backend never called `GdiplusStartup`.** Every GDI+ call
   returned GdiplusNotInitialized and left its handle null, so
   `GdipSetStringFormatAlign` dereferenced zero and `size-text` segfaulted.
   Fix: `init-gdiplus` in modules/view/backends/windows/gui.reds, called from
   `init`; imports added to win32.reds.

Verification at 190: fixed point holds (190 vs 191 differ in 17 bytes of
build-clock noise); Red/System suite 12680/12680; headless View 246/246;
`v3.red` prints `window-and-widgets-created` where the 187 build printed three
`CreateWindowEx failed!` and segfaulted.

Remaining, cosmetic: gui-console prints two `Math Error: attempt to divide by
zero` at startup -- `view/flags/no-wait win [resize]` fires `on-resizing`
before `terminal/update-cfg` measures the font, so `adjust-console-size`
divides by a still-zero `char-width`/`line-h`. `update-cfg` runs right after
and fixes them, so the console is fine once up. App-level ordering wart.

## CORRECTION: the 1.85 MB Darwin spread was the output file name

Not a real nondeterminism. The output file name is embedded in the image and
its **length** shifts the serialized data exactly like the build date does,
but far more violently. Measured (all from `red-toolchain-darwin-hybrid.red`):

    dt19a(5)  vs dt194 (5)   =      70     <- built a session apart
    dt194b(6) vs dt194c(6)   =      68
    dt194 (5) vs dt195 (5)   =     139
    dt194b(6) vs dt195b(6)   =     140
    dt19a(5)  vs dt194b(6)   = 1848597     <- built minutes apart
    dt194 (5) vs dt194c(6)   = 1848595

Equal length -> noise floor (68-140). One char of length -> ~1.85 MB. It is
length only, not content: dt19a vs dt194 differ in content, agree to 70.

Localization: of 1,835,512 differing bytes, 1,830,687 are in `__DATA,__data`
(2,144,688 total) and only 4,825 in `__TEXT,__text` (4,544,468) -- i.e. the
code is essentially identical, the embedded image is what moves.

Rule: **always compare generations with output names of equal length**, or the
diff is dominated by the shift and looks like a regression.

## BUG FOUND + FIXED: ARM64 stack args packed wrong on Darwin (Apple != AAPCS64)

Running the 41-unit Red/System suite on Darwin-ARM64 for the first time
showed `struct-x64-test` at **626/628** while Linux-ARM64 was 628/628.
Instrumented the `x64-native-aggregate-abi` test (built
`build/tmp-imp/probe/units/sx64probe.reds`, every `--assert` turned into
`print-line either ... ["Mnnn ok"]["Mnnn FAIL"]`): **M16 and M17** fail, and
only on Darwin.

    M16: 1 = checkBigOverflow 1 2 3 4 5 6 7 s3 8 42
    M17: 1 = callBigOverflowCallback as int-ptr! :big-overflow-callback

- AGENTS.md already said "Apple's ARM64 ABI follows AAPCS64 for non-variadic
  stack arguments, so the wider slots are right there too; what is missing is
  a run, not a reason." **That assumption is false** -- and it was the
  justification for the earlier fix that made Linux correct.
- Ground truth from the platform C compilers (compiled `callbig.c` /

      Darwin  x@sp+0  y@sp+4        (two ints after x0-x7 exhausted)
      Linux   x@sp+0  y@sp+8
      Darwin  char@0  short@2  int@4
      Linux   char@0  short@8
      Darwin  b@0 tail@16 marker@20
      Linux   b@0 tail@16 marker@24
  So Apple packs each stack argument at its **own alignment** with no
  8-byte rounding: slot = align(size, alignment), stack-align = alignment.
  AAPCS64: slot = align(size, 8), stack-align = max(alignment, 8).
- Fix: `system/codegen/arm64-codegen.reds`, `abi-parameter-location`, the one
  `stack-align`/`slot` pair that every stack branch shares, now branches on

### Debugging technique that paid off
`--dump-o2-ir <file>` plus a Python decoder of the RSIR tables
(`build/tmp-imp/gc/irparse.py`) turns "codegen INVALID_IR site N in
function=2806 instruction=709" into the exact source construct. Table order
is header(44) types(20) members(8) imports(32) globals(24) functions(36)
exports(12) parameters(8) initializers(16) switches(12) instructions(16)
lines(16) file-table(8) strings. **The parameter count must include each
function's parameters *and* locals**, not just the imports'.
`codegen-diag` reports `function=`/`instruction=` from `mark-function`, which
arm64's main loop calls *after* `plan-function` — so a plan-phase failure
names the **previous** function.

### Two runtime defects found while smoke-testing (NOT fixed, separate work)

1. GTK3 backend, 64-bit pointer truncation. Fixed two instances:
   `gui.reds set-defaults` had `font [integer!]` receiving the gchar* that
   `g_object_get` writes for "gtk-font-name"; `css.reds set-env-theme`
   indexed `g_strsplit`'s gchar** through a `handle!`, which indexes in
   integer! units. A third instance remains: a wrapper calls
   `g_object_get_qdata(widget, quark)` with a widget whose upper 32 bits are
   gone (`0x559c4180` = low half of `0x5555559c4180`). Symptom is
   `*** Runtime Error 1: access violation` before any window opens.
2. Darwin-ARM64 `objc_msgSend`. Apple's ARM64 ABI spills *every* variadic
   argument to the stack — clang emits `f(1,2,3,4)` as `w0=1` with 2/3/4 at
   sp+0/+8/+16 — but `objc_msgSend(id self, SEL op, ...)` has two *named*
   parameters that must stay in x0/x1. cocoa.reds declares it
   `[[variadic objc]]` with zero declared parameters, so
   `argument-count > call-parameter-count` is true for all three and the
   backend spills all of them; x0/x1 keep stale values. lldb on the Mac:
   `x1 = 0x100288b51` ("dButton", a string literal), receiver RedButtonCell
   -> `+[RedButtonCell dButton]: unrecognized selector`. `arm64-codegen`
   has no notion of the `objc` attribute at all (compiler-core uses it only
   to suppress float32! promotion), so a fix belongs in the backend or in
   the cocoa.reds declaration, and needs checking on all three ARM64/Linux
   paths before it is committed.

## 51. Darwin-ARM64 gui-console now RUNS (objc_msgSend ABI)

Fixed the defect recorded at the end of section 50. The **legacy** ARM64
target, `system/targets/ARM64.red` `emit-call-import`, already knew the
answer:

    apple-call?:      all [apple-aarch64? external-abi-call? fspec]
    objc-call?:       compiler-api/find-attribute fspec/4 'objc
    apple-variadic?:  all [apple-call? fspec/3 = 'cdecl
                           compiler-api/variadic? args/1
                           not objc-call?]

i.e. an `objc` import is **exempt** from Apple's "spill every variadic
argument" rule -- it is passed with `prepare-call-args/apple-abi`, all
arguments in registers. Verified against clang on the Mac, which compiles
`f(1,2,3,4)` as `w0=1` with 2/3/4 at sp+0/+8/+16: the named argument keeps
its register and only the variadic tail is spilled.

The new backend had no such exemption. In `arm64-codegen.reds` the trailing
branch was `either target-abi = ABI_AAPCS64 [abi-trailing-argument ...]
[stack-offset: (slot - call-parameter-count - 1) * 8]`, and cocoa.reds
declares `objc_msgSend` as `[[variadic objc]]` with **zero** declared
parameters -- so `slot > call-parameter-count` held for all three arguments
and every one of `objc_msgSend [cls sel arg]` went to the stack with x0/x1
left holding junk. The fix is one line at that branch:

    either any [target-abi = ABI_AAPCS64 (call-flags and OBJC) <> 0][...]

`OBJC: 128` was already defined in arm64-codegen and already set by
`compiler/rsir-frontend.red` (`objc-flag: 128`); nothing used it. Note
`objc_msgSendSuper` in cocoa.reds has always spelled its two named
parameters out -- declaring them on `objc_msgSend` instead was tried first
and works for the frontend but moves ~750 call sites under a new
`implicitly-compatible?` check, so the backend fix is the one to keep.
